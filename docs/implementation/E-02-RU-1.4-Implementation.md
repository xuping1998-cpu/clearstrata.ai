## 1. Purpose

Define the **executable evidence package design** for **RU-1.4 — Executable Verification Evidence Package**.

RU-1.4 **proves** (when separately authorized and executed) that:

- RU-1.1 Primary Audit physical foundation
- RU-1.2 atomic transaction / ownership / reconciliation envelope
- RU-1.3 Runtime COMMITTED authority evaluator

satisfy certified E-02 contracts in an **authorized database environment**.

RU-1.4 **does not redesign** certified contracts. If executable tests expose defects → **FAIL** → route to appropriate RU remediation governance. **No silent repair during evidence execution.**

- No Primary Audit
- Lock released

## 16. Failure injection design + testability gap

**Constraint:** Production RPC has **no** test-only failure-injection parameter. **Do not modify** RPC without separate authorization.

### Legitimate failure induction (proposed)

| Failure | Input / setup |
|---------|---------------|
| Duplicate primary audit id | Reuse `p_primary_audit_id` |
| Duplicate attempt id | Second call with conflicting identity |
| Invalid freeze event / meeting correlation | Mismatched UUID params |
| Invalid boundary | Null / misaligned timestamp |
| Source-state precondition failure | Missing voters / resolutions |

### Testability gap (Design Review)

**ERQ-1.4-005 — PROPOSED / DESIGN REVIEW:**

Deterministic mid-envelope failure **after** B/C/D/E writes but **before** G may be ** difficult** without:

- controlled source-state that fails final verification, or
- authorized test hook (not in current RPC)

If Design Review confirms gap → document **TESTABILITY GAP** · scope rollback evidence to **pre-G input failures** + **post-commit absence proofs** until hook authorized.

## 17. Concurrency fixture — EIR-048

**Fixture ID:** `EEP-EIR-048-001` — **MANDATORY**

### Scenario

Two real sessions · same meeting · overlapping time window:

| Session | Action |
|---------|--------|
| **A** | Acquires advisory xact lock (via RPC entry or harness holding same lock namespace) |
| **B** | Calls RPC while A holds lock |
| **B expected (during overlap)** | `RETRYABLE` |
| **A** | Completes → `ATOMIC_ENVELOPE_COMPLETE` |
| **B** (after A) | `IDEMPOTENT_RETURN` or certified reconciliation path |

### Verify

- Exactly one primary event
- Exactly one Primary Audit
- No duplicate materialization

**EEP-6:** Sequential calls **do not** prove concurrency. Requires genuinely overlapping transactions.

## 18. Lock-hold mechanism (Design Review)

**ERQ-1.4-004 — PROPOSED**

RU-1.2 RPC may complete too quickly for race without harness.

**Proposed mechanisms (Design Review must select one):**

| Option | Description |
|--------|-------------|
| **H1** | Harness Session A: `BEGIN` · acquire same advisory lock key as RU-1.2 · hold · Session B: invoke RPC |
| **H2** | Two parallel RPC attempts with barrier synchronization |
| **H3** | `pg_sleep` in **test harness only** (never production RPC) while holding advisory lock |

Must prove **same lock semantics** as RU-1.2 ownership namespace. **No production sleep.**
