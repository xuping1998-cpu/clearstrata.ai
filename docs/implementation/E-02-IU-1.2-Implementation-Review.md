## 6. Outcome Decision Table

Authoritative validation outcomes for IU-1.2 implementation readiness:

| Condition | Expected outcome | Recommended next action | Notes |
|-----------|------------------|-------------------------|-------|
| All permanent preconditions satisfied; **no** existing freeze conflict | **VALID** | `OPEN_TRANSACTION` | Hand off to Candidate identity (IU-1.1) → IU-1.3 |
| Permanent architectural or meeting precondition fails | **INVALID** | `ABORT` | Fail closed (FA-4, PI-3) |
| **Committed primary** Freeze Event already exists for meeting | **IDEMPOTENT RETURN** *(RA-004)* | `RETURN_EXISTING_FREEZE` | Return existing committed primary id; **no** new event; **not** a failure |
| Another **non-terminal** freeze attempt owns the boundary | **RETRYABLE** *(DA-001)* | `RETRY` | No durable identity assigned; retry after contention clears |
| Transient infrastructure, transaction ownership, or locking prevents safe continuation | **RETRYABLE** | `RETRY` | RM-2 |

### IDEMPOTENT RETURN (RA-004)

When a committed primary Freeze Event exists:

- The **existing committed primary** Freeze Event **shall** be returned as the authoritative freeze identity.
- A **new** Freeze Event **shall not** be created.
- This condition **shall not** be treated as an implementation failure.
- Orchestration may indicate freeze was **already committed**.

*Implementation note:* Expressed as `CONFLICT` outcome with `RETURN_EXISTING_FREEZE` action in design examples, or as a dedicated orchestration branch — runtime mapping verified in Engineering Implementation Review. **Semantic contract is IDEMPOTENT RETURN.**

### CONFLICT semantics

**CONFLICT** is **reserved** for a durable state conflict that **cannot** be safely interpreted as:

- idempotent committed-primary return,
- permanent validation failure (`INVALID`), or
- transient retry condition (`RETRYABLE`).

**Review finding:** No currently authorized E-02 Phase 1 condition **requires** emission of `CONFLICT` as the terminal validation decision once RA-004 and DA-001 are resolved. The outcome **may remain reserved** for future contract-compatible use. **No new business rule invented** to force CONFLICT usage.

## 12. Implementation findings

### Conforming design

| # | Finding |
|---|---------|
| I-1 | Validation Contract complete with four terminal decision classes plus authoritative IDEMPOTENT RETURN semantics (RA-004) |
| I-2 | Five-stage deterministic pipeline aligns with Design Review 31/31 PASS |
| I-3 | `FreezeContext` mutation boundary consistent with IU-1.1 completion baseline |

### Validation semantics

| Outcome | Semantics (authoritative) |
|---------|---------------------------|
| **VALID** | Open transaction path permitted |
| **INVALID** | Permanent precondition failure — abort |
| **RETRYABLE** | Transient or contention — retry (DA-001) |
| **IDEMPOTENT RETURN** | Committed primary exists — return existing id (RA-004) |
| **CONFLICT** | Reserved — no Phase 1 condition requires emission |

### Outcome exclusivity and completeness

**PASS** — mutually exclusive terminal decisions; collective completeness achieved with RA-004 as explicit idempotent branch (not a fifth enum required at design level — orchestration maps to `RETURN_EXISTING_FREEZE` action).

### RA-004 closure

**RESOLVED** — **IDEMPOTENT RETURN** when committed primary exists. Consistent with Architecture Authority §13 idempotency and INV-8 (no new primary identity).

### DA-001 closure

**RESOLVED** — **RETRYABLE** when non-terminal attempt owns boundary. Consistent with RM-2 and single transaction ownership (R-003).
