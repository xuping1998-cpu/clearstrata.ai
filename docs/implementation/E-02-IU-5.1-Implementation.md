## 3. Verification Result Taxonomy

| Result | Definition |
|--------|------------|
| **PASS** | Current repository and/or executable evidence **proves** the obligation is satisfied **now**. |
| **FAIL** | Executable mechanism **exists**, but empirical evidence **violates** the obligation. |
| **NOT IMPLEMENTED** | Obligation requires an executable mechanism that **does not exist** in repository head. |
| **BLOCKED** | Obligation cannot be executed because a **prerequisite** executable mechanism is missing. |
| **PENDING EXTERNAL EVIDENCE** | Static repository insufficient; requires deployment/runtime/DB fixture evidence not available in this verification pass. |
| **NOT APPLICABLE** | Authority proves obligation does not apply to current E-02 scope (must cite authority). |

**Prohibited labels:** UNKNOWN · MAYBE · ASSUMED PASS · design-only PASS substituted for executable PASS.

## 4. Evidence Classes

| Class | Description | May alone prove executable PASS? |
|-------|-------------|----------------------------------|
| **EC-1** | Repository static evidence (source code structure, exports, read paths) | **Yes** — for static/read-only obligations only |
| **EC-2** | Migration / schema evidence (tables, columns, indexes in repo migrations) | **Yes** — for schema-existence obligations only |
| **EC-3** | Database constraint evidence (UNIQUE, FK, triggers in migrations) | **Yes** — for constraint-existence; **No** — for runtime race behavior alone |
| **EC-4** | Executable orchestration evidence (write path, RPC, transaction holder) | **Yes** — when mechanism exists and is verified |
| **EC-5** | Automated test evidence | **Yes** — when tests exist and were executed |
| **EC-6** | Runtime transaction evidence | **Yes** — for COMMIT/rollback/audit runtime obligations |
| **EC-7** | Production / deployment evidence | **Yes** — when explicitly required and collected |
| **EC-8** | Certified design authority (Phase 1–4 Certification, Architecture Authority) | **No** — proves **contract only**, not executable satisfaction |

**Example:** `NO PRIMARY AUDIT → NO COMMITTED FREEZE` — **EC-8 PASS** (contract certified). Primary Audit INSERT works atomically — requires **EC-4/EC-6**; **EC-8 alone is insufficient**.

## 7. Deduplication Methodology

1. Collected all **143** source obligations with original IDs preserved.
2. Grouped by **semantic intent** (same runtime claim = one canonical item).
3. Mapped every source ID → exactly one **EIR-** canonical ID.
4. Where 4.1 and 4.2 test the same read-path behavior, **4.2 retained as primary source** (integration verification superset); 4.1 IDs mapped to same canonical.
5. Where Phase 3 and Phase 4 repeat boundary invariants (no legacy RPC, no status UPDATE, no live reconstruction, gap visibility), **one canonical** item retained with multi-source traceability.
6. **No obligations dropped** — every raw ID maps to a canonical item.
